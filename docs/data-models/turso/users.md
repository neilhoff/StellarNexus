# Better Auth Data Model - Turso SQLite

## Overview

StellarNexus uses **Better Auth** with **Turso SQLite** as the authentication backend. The data model consists of 4 core tables managed by Better Auth, with custom extensions for role-based access control and user management.

**Database**: Turso (libSQL/SQLite-compatible)  
**ORM**: Better Auth with Turso adapter  
**Schema Location**: `scripts/auth-schema.sql`

---

## Tables

### 1. `user` Table

Stores user identity, credentials, and authorization metadata.

| Column | Type | Constraints | Description |
|--------|------|-------------|-------------|
| `id` | TEXT | PRIMARY KEY | UUID (generated by Better Auth) |
| `email` | TEXT | UNIQUE NOT NULL | User email (normalized to lowercase) |
| `email_verified` | INTEGER | DEFAULT 0 | 1 = verified, 0 = unverified |
| `name` | TEXT | NULLABLE | Display name |
| `image` | TEXT | NULLABLE | Avatar URL (not currently used) |
| `roles` | TEXT | DEFAULT `'["user"]'` | JSON array of role strings |
| `disabled` | INTEGER | DEFAULT 0 | 1 = disabled, 0 = active |
| `disabled_at` | TEXT | NULLABLE | ISO timestamp when disabled |
| `disabled_by` | TEXT | NULLABLE | Email of admin who disabled |
| `created_at` | TEXT | NOT NULL | ISO timestamp |
| `updated_at` | TEXT | NOT NULL | ISO timestamp |
| `last_sign_in_at` | TEXT | NULLABLE | ISO timestamp of last login |

**Custom Fields** (defined in `betterAuth.mjs`):
- `roles` - JSON string array, returned in session responses
- `disabled` - Boolean flag, returned in session responses

**Indexes**:
- `idx_user_email` on `email` (also UNIQUE constraint)

**Role Values**:
- `user` - Default role for all users
- `admin` - Can access admin features
- `super-admin` - Full administrative access, can manage other admins

**Usage Pattern**:
```javascript
// Parse roles from JSON string
const roles = JSON.parse(user.roles || '["user"]')
const isAdmin = roles.includes('admin') || roles.includes('super-admin')
const isSuperAdmin = roles.includes('super-admin')
```

### 2. `session` Table

Stores active user sessions with expiration tracking.

| Column | Type | Constraints | Description |
|--------|------|-------------|-------------|
| `id` | TEXT | PRIMARY KEY | UUID |
| `user_id` | TEXT | NOT NULL, FOREIGN KEY | References `user.id` |
| `token` | TEXT | UNIQUE NOT NULL | Session token (cookie value) |
| `expires_at` | TEXT | NOT NULL | ISO timestamp |
| `created_at` | TEXT | NOT NULL | ISO timestamp |
| `updated_at` | TEXT | NOT NULL | ISO timestamp |

**Configuration** (from `betterAuth.mjs`):
- `expiresIn`: 7 days (604800 seconds)
- `updateAge`: 1 day (86400 seconds) - session is refreshed if accessed within this window before expiry

**Indexes**:
- `idx_session_token` on `token`
- `idx_session_user_id` on `user_id`

**Cookie Name**: `stellar-nexus.session_token` (configured via `advanced.cookiePrefix`)

**Usage Pattern**:
```javascript
// Validate session and get user
const result = await db.execute({
  sql: `SELECT s.token, s.expires_at, s.user_id, u.email, u.name, u.roles, u.disabled
        FROM session s JOIN user u ON s.user_id = u.id
        WHERE s.token = ?`,
  args: [token]
})

// Check expiration
const expiresAt = new Date(row.expires_at)
if (expiresAt < new Date()) return null // expired
```

### 3. `account` Table

Stores OAuth/social provider accounts linked to users (not currently used, but available for future OAuth integration).

| Column | Type | Constraints | Description |
|--------|------|-------------|-------------|
| `id` | TEXT | PRIMARY KEY | UUID |
| `user_id` | TEXT | NOT NULL, FOREIGN KEY | References `user.id` |
| `provider_id` | TEXT | NOT NULL | OAuth provider (e.g., "google", "github") |
| `provider_account_id` | TEXT | NOT NULL | Provider's user ID |
| `access_token` | TEXT | NULLABLE | OAuth access token |
| `refresh_token` | TEXT | NULLABLE | OAuth refresh token |
| `expires_at` | INTEGER | NULLABLE | Unix timestamp |
| `created_at` | TEXT | NOT NULL | ISO timestamp |
| `updated_at` | TEXT | NOT NULL | ISO timestamp |

**Indexes**:
- `idx_account_user_id` on `user_id`

**Current Status**: Table exists but no OAuth providers are configured. Email/password auth is used exclusively.

---

### 4. `verification` Table

Stores email verification tokens and password reset tokens.

| Column | Type | Constraints | Description |
|--------|------|-------------|-------------|
| `id` | TEXT | PRIMARY KEY | UUID |
| `identifier` | TEXT | NOT NULL | Email address or other identifier |
| `value` | TEXT | NOT NULL | Verification token |
| `expires_at` | TEXT | NOT NULL | ISO timestamp |
| `created_at` | TEXT | NOT NULL | ISO timestamp |
| `updated_at` | TEXT | NOT NULL | ISO timestamp |

**Usage**:
- Email verification tokens (when `requireEmailVerification: true`)
- Password reset tokens (generated by `forgetPassword` API)

**Current Status**: Email verification is disabled (`requireEmailVerification: false`), but password reset flow uses this table.

## Relationships

```
user (1) ──< (N) session
  │
  └────< (N) account
```

- **user → session**: One-to-many. A user can have multiple active sessions (multiple devices/browsers)
- **user → account**: One-to-many. A user can link multiple OAuth accounts (future use)
- **session → user**: Many-to-one. Each session belongs to exactly one user

## Authentication Flow

### Sign Up
1. Client calls `POST /api/auth` with `{ action: "signUp", email, password, name }`
2. Better Auth hashes password, creates `user` record with `roles: '["user"]'`
3. Better Auth creates `session` record with 7-day expiry
4. Returns `{ user, session: { token, expiresAt } }`
5. Client stores token in cookie or localStorage

### Sign In
1. Client calls `POST /api/auth` with `{ action: "signIn", email, password }`
2. Better Auth validates credentials against `user` table
3. Checks `disabled` flag - rejects if `disabled = 1`
4. Creates new `session` record
5. Updates `user.last_sign_in_at`
6. Returns session token

### Session Validation
1. Client sends `Authorization: Bearer <token>` header
2. Server queries `session` table by token
3. Joins with `user` table to get user data
4. Checks `expires_at` - rejects if expired
5. If session is within `updateAge` window, extends `expires_at`
6. Returns user identity with parsed roles

### Sign Out
1. Client calls `POST /api/auth` with `{ action: "signOut", token }`
2. Better Auth deletes `session` record
3. Cookie is cleared

## Role Management

### Role Hierarchy
```
super-admin > admin > user
```

### Role Checks
```javascript
// From authIdentity.mjs
const roles = JSON.parse(row.roles || '["user"]')
const isSuperAdmin = roles.includes('super-admin')
const isAdmin = isSuperAdmin || roles.includes('admin')
```

### Granting Roles
**Bootstrap** (initial super-admin):
```bash
node scripts/bootstrap-users.mjs
# Interactive prompts for email, password, name
# Creates user with roles: '["user","super-admin"]'
```

**Admin API** (subsequent grants):
```javascript
// From src/http/post-api-admin-users-update/index.mjs
await db.execute({
  sql: 'UPDATE user SET roles = ?, updated_at = ? WHERE email = ?',
  args: [JSON.stringify(newRoles), new Date().toISOString(), email]
})
```

### Disabling Users
```javascript
// From src/http/post-api-admin-users-disable/index.mjs
await db.execute({
  sql: `UPDATE user SET disabled = 1, disabled_at = ?, disabled_by = ?, updated_at = ?
        WHERE email = ?`,
  args: [new Date().toISOString(), disabledBy, new Date().toISOString(), email]
})
```

Disabled users cannot sign in. The check happens in `handleSignIn` before session creation.

## Schema Migration

**Initial Setup**:
```bash
turso db shell stellar-nexus-dev < scripts/auth-schema.sql
```

**Adding Custom Fields** (already done):
The `roles` and `disabled` fields are custom additions to Better Auth's default schema. They're defined in `betterAuth.mjs` under `user.additionalFields`.

**Future Migrations**:
Better Auth doesn't have built-in migrations. Manual SQL or a migration tool like `drizzle-kit` would be needed for schema changes.

## Security Considerations

1. **Password Storage**: Better Auth uses bcrypt/scrypt hashing. Never store plaintext passwords.
2. **Session Tokens**: Cryptographically random, stored in `session.token` column
3. **Token Expiration**: 7-day default, configurable in `betterAuth.mjs`
4. **Disabled Users**: Checked on every sign-in attempt
5. **Role Validation**: Always verify server-side, never trust client-provided roles
6. **Audit Trail**: `disabled_at` and `disabled_by` track who disabled a user and when
